# Commit Formulation, Staging & PR Delivery

This document specifies the rules for staging files, generating compliant Conventional Commit messages, pushing to remote, and creating structured Pull Requests via GitHub CLI.

---

## 1. Conventional Commit Formulation

All commits generated by `git-ship-acrazie` must adhere to the Conventional Commits 1.0.0 specification.

### Structure
```text
<type>(<scope>): <short summary in imperative mood>

[optional body explaining motivation and key decisions]
```

### Types
- `feat`: New user-facing capability or functionality.
- `fix`: Bug fix or patch addressing unintended behavior.
- `chore`: Maintenance, dependencies, tool configuration, or repo plumbing.
- `docs`: Documentation updates, guides, README changes only.
- `refactor`: Code reorganization that neither fixes a bug nor adds a feature.
- `test`: Adding or modifying tests and test suites.
- `ci`: Changes to CI/CD workflows and deployment configurations.
- `perf`: Code changes that improve performance.

### Style Rules
- **Imperative present tense**: "add feature" (not "added feature" or "adds feature").
- **Lowercase header**: Start summary with a lowercase letter, do not end with a period.
- **Meaningful Scope**: Reflect the impacted subsystem or component (e.g., `feat(auth): ...`, `fix(renderer): ...`, `chore(deps): ...`).

### Hard Invariant: No Co-Author Trailers
**NEVER** append `Co-authored-by: ...` or any automated co-author attributions. Ensure the commit author is clean.

---

## 2. Targeted Staging Protocol

1. Never run blanket `git add .` unless every single untracked and modified file was verified and intentional.
2. Stage specifically the files modified or created for the completed task:
   ```bash
   git add path/to/file1 path/to/file2
   ```
3. Run `git diff --cached --stat` to verify only intended files are in the staging area.

---

## 3. Remote Push Protocol

1. Push with upstream branch tracking:
   ```bash
   git push -u origin <branch-name>
   ```
2. If pushing fails due to network or authentication:
   - Check `git remote -v`.
   - Report the error without attempting unsafe force-pushes.
   - Never run `git push --force` or `git push -f` autonomously.

---

## 4. Pull Request Creation via GitHub CLI (`gh`)

### Mode: Default to Draft
To allow the user and reviewers to inspect the PR before triggering full deployment or notification pipelines, always create the PR as a **Draft** by default:
```bash
gh pr create --draft --title "<pr-title>" --body "<pr-body>"
```
*(Omit `--draft` only if the user explicitly commanded a ready/public PR).*

### PR Title
The PR title must match the Conventional Commit header:
```text
feat(scope): concise description
```

### PR Body & Template Compliance
Inspect `.github/pull_request_template.md` (or `.github/PULL_REQUEST_TEMPLATE.md`). Populate its sections dynamically based on the git diff:
1. **Summary**:
   - 2-3 sentences explaining what was built/fixed and why.
2. **Related Issue**:
   - `Closes #<issue-number>` or `N/A`.
3. **Type of Change**:
   - Check the relevant boxes (`[x]`).
4. **Changes list**:
   - Bullet points detailing key modifications.
5. **Testing & Verification**:
   - Commands executed and validation results (`passed linting, unit tests 12/12`).
6. **Checklist**:
   - Check confirmed items.

If no PR template exists in `.github/`, use this structured default:
```markdown
## Summary
<concise summary of changes>

## Changes
- <bullet 1>
- <bullet 2>

## Verification
- Pre-flight quality gates passed
- Conventional Commits enforced
```
