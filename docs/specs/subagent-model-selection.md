# User-validated subagent model selection

## Objective and scope

Add portable, task-sensitive model selection to the four delegating workflows:
`diagnostic-queue-runner-acrazie`, `feature-builder-acrazie`,
`repository-readme-architect-acrazie`, and `mechanical-port-acrazie`.
Carry the same gate into workflows generated by `multi-agent-planner-acrazie`
without making that planner execute agents.

Each skill embeds the complete section so installation of a single skill does not
depend on repository-wide instructions or an additional policy skill. Keep the
sections consistent. Extend the existing glossary and platform adaptation notes.
Do not alter invocation metadata, introduce an orchestrator, change existing
review/test gates, configure providers, or install dependencies.

## Approved decisions

- Verify models available to the actual runtime/account and whether it supports
  selecting a subagent's model. Provider catalog presence alone is insufficient.
- Propose 2–3 verified options, or fewer when fewer are verifiable. Give exactly one
  recommendation based on the lot's task, complexity, risk, and capabilities.
  Describe cost/capacity/latency only with supporting evidence; disclose unknowns.
  If no selectable option is verifiable, ask without inventing a recommendation.
- Prefer economical models when sufficient, not a fixed "two classes below" rule
  or hard-coded provider/model mapping.
- Wait for explicit user validation per homogeneous lot: same role, bounded
  mission/scope, risk, and model. State the lot boundary and agent count. Approval
  covers scoped retries, not later unrelated work or changed model/role/scope/risk.
- If selection is unsupported, unverifiable, or the chosen model unavailable,
  ask before using an alternative, inheritance, or a permitted non-spawn path.
  Do not silently inherit, substitute, or claim an override.
- Model validation is distinct from authorization to delegate and approval of
  the task or review. Preserve fresh-context reviewer isolation and all existing
  contracts, permissions, worker/retry limits, tests, and acceptance gates.
- Record choice and validation in existing task/workflow evidence. Distinguish the
  requested model from the actual model when reported, or disclose that the actual
  identity is unverified.
  If the runtime reports a different model, stop the lot and ask before further
  delegation.
- Loading a skill in the current context is not a spawn. The reviewer is a
  recipient, not an additional spawning workflow; Jenkins specialist loading is
  outside this change.

## Approval

Approved in the 2026-10-08 conversation invoking `grill-with-docs`. The user
accepted economical task-fit selection (Q1), requested multiple options with a
task-sensitive recommendation (Q2), chose asking on unavailable/unsupported
selection (Q3), required user validation (Q4), then chose validation "par lot".
The user replied `ok` to the consolidated modification contract.

This approval covers isolated implementation and local static validation, not
paid model trials, provider configuration, installation, deployment, or Git
publication. No new ADR is needed: this reversible instruction policy is recorded
in the contract rather than treating every task decision as architectural.

## Acceptance and proof

- C1: All five skills embed an identical standalone portable gate with verified
  options, one task-sensitive recommendation, and explicit per-lot validation.
- C2: Unsupported/unverifiable selection never silently falls back. There is no
  fixed model mapping, downgrade arithmetic, or invented availability claim.
- C3: Workflow call sites preserve separate worker/reviewer roles, fresh contexts,
  bounded retries, optional README discovery, and the planner's no-execution rule.
- C4: Generated prompts retain lot identity, options/recommendation, and validation
  status; unknown target platforms keep selection pending. A planning fast path
  does not bypass model validation.
- C5: Existing glossary is extended; frontmatter/UI metadata and skill structure
  remain intact. Local checks are not claimed as live cross-harness routing proof.

### Scenario acceptance matrix

These are required instruction outcomes, not records of live model executions.

| Scenario | Required outcome |
| --- | --- |
| README discovery, three verified choices | Propose choices, recommend task-fit economical option, wait before optional spawn. |
| Diagnostics workers followed by reviewers | Separate validated lots; the worker choice does not select the review model. |
| Feature review accepted, model not selected | Offer reviewer choices; review acceptance alone does not permit model selection. |
| Re-review of changed snapshot within the same approved mission/risk/model | Reuse valid lot approval, but create a fresh reviewer context and review the new fixed snapshot. |
| Model unavailable, one verified alternative, or override unsupported | Show only verified choices and ask; inheritance requires explicit user acceptance. |
| Unknown platform or planner fast path | Output a pending model-selection gate; do not spawn or invent target identifiers. |
| Required reviewer isolation incompatible with selected mechanism | Ask for an isolation-preserving alternative; do not fall back to self-review. |
